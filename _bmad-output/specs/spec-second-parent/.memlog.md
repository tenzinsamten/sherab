topic: Second parent linked to a student, with equal parent access
updated: 2026-10-27T06:34
---

- (direction) User: a student can be linked to only one parent (one email); one parent cannot always check on the children, so both parents must be able to view their children's information.
- (decision) Reverses parent-role PRD §6 'one Parent account per family' and AD-10's single profiles.parent_id link.
- (decision) Linking: the already-linked parent invites the second parent by email (user choice over admin linking, self-request, two emails at registration).
- (decision) Rights: the second parent has exactly the same access as the first: every parent read (AD-12), session leave (AD-13), deletion requests (AD-9), homework push (#92), the child on /parent.
- (decision) Limit: at most two linked parents per student, enforced in the database.
- (decision) Mode: express distill; gaps become open questions.
- (capability) CAP-1 A linked parent invites a second parent for their child by email, sees the pending invite, and can cancel it.
- (capability) CAP-2 The invited person becomes a linked parent once they hold an approved parent account with the invited email and accept the invite.
- (capability) CAP-3 Both linked parents get identical parent access to the child; neither parent's access depends on the other.
- (capability) CAP-4 The admin sees both parents of each student and can remove a parent link.
- (constraint) At most two parents per student, enforced in the database, not only in the UI (AD-2).
- (constraint) The link is stored, set only by trusted paths; RLS never matches email text (AD-10 carried over). The invite email only identifies whom the invite is for.
- (constraint) Every existing is_parent_of / linked_children / parent-recipient check covers both parents through the shared helpers; no parallel read path (AD-12).
- (constraint) Only an approved parent linked to the child can invite, and only for that child.
- (constraint) A student always keeps at least one linked parent; removing the last link is refused (ON DELETE RESTRICT spirit of AD-10).
- (constraint) Existing single-parent students work unchanged after release; their current link becomes their first link.
- (constraint) All new text localized in en, de and bo.
- (assumption) The invitee accepts the invite on their parent page; linking is not automatic on email match, so a mistyped email cannot expose a child to a stranger.
- (assumption) The app does not send an invite email; the inviting parent tells the second parent to register with that email. An existing approved parent sees the invite on /parent.
- (assumption) Session leave set by either parent is one shared answer per session; the latest change wins and the history records who set it.
- (question) Who besides the admin may remove the second parent: the first parent, the second parent themself, or both?
- (question) Should the app email the invitation (custom SMTP exists for confirmation mail), or is telling the person enough?
- (question) Do invites expire, and is there one pending invite per child at a time?
- (question) What happens when the second parent already registered the same child separately: is a duplicate student refused, flagged to the admin, or out of scope?
- (question) Duplicate deletion requests: if one parent requests deletion, is the other parent told, and can the other parent withdraw it?
- (question) Teacher views that name 'the parent' (e.g. leave set by, guardian email): show both parents, or the one who acted?
- (note) CAP-4 (admin sees both parents, removes a link) added by the spec, not stated by the user; it covers revoking a wrong invitee. Confirm with the user.

- (decision) Removal: only the admin removes a parent link; parents cannot remove themselves or the other parent (resolves open question 1; supersedes 'who besides the admin').
- (decision) Safeguard: a link takes effect on accept; the admin's student page shows each parent, who invited them and when.
- (decision) Deletion with two parents: a pending deletion request shows on both parents' child page with who requested it; the second parent gets an 'already requested' message, not an error; the admin decides as today.
- (decision) Duplicates: /join refuses a registration when the registering parent has a pending or accepted invite for a child with the same name (trimmed, case-insensitive), pointing them to the invite. Supersedes non-goal 'merging duplicates' only in that prevention is now in scope; merging stays out.
- (decision) No invite email: the inviter tells the other parent; the invite shows on /parent to an approved parent with that email (resolves open question 2; assumption becomes decision).
- (decision) Invites: one pending invite per child; expires after 30 days; the inviter can cancel and re-invite; a pending invite does not use a parent slot (resolves open question 3).
- (decision) Teacher and admin views list both parents' emails as contacts; leave and sick entries show which parent set them (resolves open question 6).
- (capability) CAP-5 /join refuses registering a child the registering parent was already invited to, and points them to the invite.
- (capability) CAP-6 Teachers and the admin see both linked parents as the child's contacts, and which parent set each leave or sick answer.
- (constraint) Limits hold under concurrency: two accepts, an accept and an invite, or two removals at the same time can never yield three links or zero links.
- (constraint) Invite matching: the email is compared trimmed and case-insensitive against the invitee's current profile email at read and accept time; the invitee reads and accepts only through a trusted server-side function, never an email-matching RLS policy.
- (constraint) Refused invites: the inviter's own email and a parent already linked to the child. The invite form never reveals whether an email has an account; the only distinct refusals are 'not your child' and 'child already has two parents'.
- (constraint) Accept re-checks in one step: invite still pending and unexpired, inviter still linked, student still exists, child below two links.
- (constraint) Removing the inviter's link, or rejecting or deleting the student, cancels the child's pending invite.
- (constraint) At-least-one-link applies to removing a link from a student who still exists; an approved deletion (AD-9) removes all links. Deleting a parent account stays refused while that parent is any student's only link, and removes only that parent's links when a co-parent remains.
- (constraint) Every direct profiles.parent_id reader moves to the link model; known readers listed in brownfield.md; acceptance: no parent lookup outside the shared helpers.
- (constraint) AD-12 write exceptions extend to: linked parents create and cancel invites; links are created only by the trusted accept path; no direct parent write to links.
- (constraint) Leave rules (AD-13 cutoffs, sick rejection final, frozen classification) apply per student and session whichever parent writes; B cannot re-submit sick after A's was rejected; history records the setting parent.
- (constraint) The admin cannot remove a link on a child they are a parent of (AD-4 self-decision guard).
- (constraint) Migration copies each non-null parent_id into one link, stops before changing anything if a row would break the new rules, and leaves parentless fixture students untouched; existing parents see the same data before and after.
- (assumption) Invites are only for approved children; pending or rejected children cannot get a second parent until approved.
- (assumption) A parent the admin removed cannot be re-invited for that child, so a re-invite cannot undo the admin's removal.
- (assumption) A linked parent who loses parent approval keeps the link but has no access (is_parent_of requires approval); the admin can remove the link to free the slot.
- (assumption) guardian_email stays the registration-time display copy; contact lists come from the links.
