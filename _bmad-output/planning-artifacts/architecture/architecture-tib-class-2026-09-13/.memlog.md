- (decision) Security model clarified for user: RLS/Security Rules enforce row-level authorization server-side regardless of client tampering (client is always untrusted). But client-computed award logic (badges, streaks) is a distinct, real risk - a tampered client could self-award. Resolves to: RLS/rules gate plain CRUD (attendance, homework CRUD, marking Done); computed/awarded values (badge crossing, streak counts, leaderboard ranking, recurring-instance generation, deletion cascade) must live in server-side functions (Postgres functions/triggers or Edge/Cloud Functions), never trust a client-submitted computed value for these.
- (decision) User confirmed: go with SvelteKit + Supabase, hybrid RLS-direct-access + function-sidecar pattern. Paradigm name: RLS-Gated Direct-Access BaaS with Function Sidecar.
- (decision) AD-1 Stack & access paradigm. Binds: all. Prevents: divergent backend choices per feature, ad hoc REST layer duplication. Rule: all persistence goes through one Supabase Postgres project; client talks to Supabase directly via its SDK, no custom REST/GraphQL layer; SvelteKit serves the frontend as an installable PWA.
- (decision) AD-2 Authorization enforcement boundary. Binds: CAP-1, CAP-2, CAP-3, CAP-7. Prevents: a feature checking permissions in frontend code, letting a tampered client bypass it. Rule: all authorization is enforced by Postgres RLS policies keyed on authenticated identity/role; frontend may hide UI per role but is never the only barrier.
- (decision) AD-3 Computed/awarded state ownership. Binds: CAP-3 (recurring generation), CAP-4 (streaks), CAP-5 (badges), CAP-6 (leaderboard rank), CAP-8 (deletion cascade). Prevents: a tampered or buggy client writing a fabricated computed value (e.g. self-awarding a badge). Rule: any computed/awarded value is written exclusively by a server-side function (Postgres function/trigger or Supabase Edge Function), never by direct client insert/update of that column/table.
- (decision) AD-4 Identity & role model. Binds: CAP-1, CAP-2, CAP-7. Prevents: divergent ad hoc 'who can see this class' checks per feature. Rule: Supabase Auth is the sole identity provider; a profiles table (PK = auth user id) carries role; a class_teachers join table expresses many-to-many teacher-class assignment; every RLS policy needing a class/role check resolves through these two tables, never a locally-invented check.
- (decision) AD-5 History-as-append. Binds: CAP-2 (skill status), CAP-3 (homework Done/Reviewed transitions), CAP-4 (attendance). Prevents: two features disagreeing on 'current value', losing substitute-teacher continuity. Rule: skill-status changes, attendance marks, and homework status transitions insert new append-only rows, never update in place; 'current' is the latest row by timestamp.
- (decision) AD-6 Deployment & environments. Binds: all. Prevents: over-building CI/CD/staging infra disproportionate to a volunteer project. Rule: frontend deploys as a static/SSR SvelteKit build to a free-tier static host (e.g. Cloudflare Pages); backend is the single managed Supabase project, no self-hosted infra; one production environment plus local dev against a separate dev Supabase project; staging deferred.
- (decision) AD-7 Ownership & portability. Binds: NFR ownership constraint. Prevents: hosting/domain/admin access tied to one individual's personal account. Rule: Supabase project, hosting account, and domain are created under an organization-owned account, never an individual maintainer's personal account.

- (decision) AD-3 tightened per adversarial review: ALL derived-state writes that react to a data change (streak recompute, badge award, deletion cascade) MUST be DB triggers on the source table write, never a client-invoked Edge Function - a trigger fires unconditionally on every write, closing the 'client never called the function' gap. Edge/scheduled functions are reserved only for genuinely time-based work with no triggering row-write: recurring-assignment instance generation. Also added: derived counts (streak length, badge-milestone crossing) must count DISTINCT (student_id, homework_instance_id) pairs reaching Done, never raw history-row counts - closes the double-insert double-count gap from AD-5 allowing both student self-mark and teacher-on-behalf-of-student inserts for the same instance.
- (decision) AD-8 (new): Recurring-instance integrity. Binds: CAP-3. Prevents: a direct client insert creating a duplicate homework_instances row for a period the recurrence sidecar already generated. Rule: a UNIQUE(assignment_id, period_start) constraint on homework_instances rejects duplicates at the DB level; RLS additionally restricts direct client inserts into homework_instances to assignments where recurrence_rule IS NULL (one-off) - instances for a recurring assignment can only be created by the trusted scheduled function's service-role connection.
- (decision) AD-9 (new): Deletion audit vs. erasure. Binds: CAP-8. This is the one explicit carve-out to 'all of that student's records are gone'; every other table is a hard delete.
