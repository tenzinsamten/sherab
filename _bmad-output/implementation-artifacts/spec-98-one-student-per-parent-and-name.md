## Intent

**Problem:** A student who fills in the public form `/join` again with another class's code gets a second account: pending, no team, no streak, new username and PIN. Approving it asks for a team again, although a student has one team for good. Today's duplicate rule is per class and name and ignores approved students, so it lets this through.

**Approach:** Decided by the user: "name + parent email should be unique". One student account per parent and name, in any class and any status, enforced in the database. `/join` refuses the second registration and, when the child is already approved, sends the family to "Join another class", which keeps the team.

## Boundaries & Constraints

**Always:**
- The rule is one student row per (`parent_id`, `lower(btrim(registration_name))`) over pending, approved and rejected rows. The database enforces it; the `/join` check is only the friendly message.
- It replaces the per-(class, name) rule: two parents may each register a child with the same name in the same class.
- A rejected registration keeps blocking the same parent and name until a teacher clears it, as today.
- Students without a parent (service-role fixtures only) are outside the rule.
- The new lookup takes a parent email and a child's name, so only the service role may call it.
- The migration deletes and changes no rows. If rows already break the rule it stops with a message that says how many and how to list them.
- New and changed texts exist in en, de and bo.

**Never:**
- No merging or deleting of existing duplicate accounts, and no push to the hosted database.
- No way for a parent to ask for another class for a linked child (separate, undecided).
- No change to approval on `/requests`, to the team set-once rule, or to "Join another class".
- No fuzzy matching: a different spelling is a different child.

## Design Notes

The lookup is service-role only because an anon-callable version would answer "does this parent have a child called X" for any email. Through the form the same answer is still visible to whoever submits a name with a parent's email; that comes with the rule, like `join_error_no_parent` already tells whether an email is an approved parent.

`parent_id` is written only by `handle_new_user()` today, so no existing path can run into the index by moving a student to another parent.

Local database on 2026-10-12: no student rows, so nothing breaks the rule here. The hosted database was not looked at.
